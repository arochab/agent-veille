## 4. Action #4 — Écriture atomique sur les fichiers mémoire critiques

**Problème (cité, P1-4)** : 7 fichiers JSON critiques (`vu.json`, `vu_sas.json`,
`signaux_frais.json`, `go_traites.json`, `tg_offset.json`, `feedback_vu.json`,
`go_suivi.json`) étaient écrits par `write_text(json.dumps(...))` direct — non
atomique. Un crash mid-write pouvait tronquer le JSON ; les loaders (tous en
`try/except → défaut`) effacent alors silencieusement toute la mémoire (ex. `vu.json`
corrompu = re-flood de vieux signaux). Fable notait aussi que dans
`feedback.py::enregistrer_event`, le registre "déjà vu" (`VU`) était écrit **avant**
l'append dans le journal (`EVENTS`) — un crash entre les deux perdait un event
"payé" pour toujours (marqué vu, jamais journalisé).

**Correctifs :**
- `systeme/atomic_io.py` (fichier créé) : fonction `write_json_atomic(chemin, objet)`
  — écrit dans un `.tmp{PID}` (nom incluant le PID pour éviter une collision entre
  deux process concurrents), puis `Path.replace()` (atomique sur le même volume,
  Windows NTFS et POSIX). Renvoie `False` sans exception remontante en cas d'échec ;
  nettoie le `.tmp` orphelin le cas échéant.
- Appliqué à : `systeme/executer_move.py:121-131` (fonction `save_json`, couvre
  `go_traites.json`, `tg_offset.json`, les snapshots go) ; `systeme/
  collecte_signaux.py` (3 sites : `VU`, `VU_SAS`, `OUT`/`signaux_frais.json`) ;
  `systeme/feedback.py` (archive radar + `VU`/`feedback_vu.json`) ;
  `systeme/suivi_go.py` (3 occurrences de `OUT.write_text` remplacées par
  `write_json_atomic(OUT, snap)`, `replace_all`).
- `systeme/feedback.py:107-116` : ordre inversé — le journal (`EVENTS.open("a")`,
  ligne 113) s'écrit **avant** `vu.add(eid)` + `write_json_atomic(VU, ...)`
  (lignes 115-116). Un crash entre les deux laisse l'event journalisé (source de
  vérité) mais pas encore marqué "vu" → au pire rejoué une 2e fois (idempotent par
  construction, sans perte), jamais perdu.

**`feedback.py` est un organe surveillé par `immunite.py`** (hash SHA-256 codé en
dur) : re-signé après modification. Hash actuel dans `systeme/immunite.py:37` :
`6f1ef69c63ce593fd95ff471fcf7a1f18e10e3c20e4c0decee892434544e31e6`. Vérifié
`immunite.verifier()` → `{'ok': True, 'halt': False, 'alteres': [], 'manquants': [],
'raison': ''}` (exécuté maintenant pour ce document, voir § 7).

**Tests exécutés :**
- `write_json_atomic` isolé : écriture normale + relecture correcte ; puis
  injection d'un objet non sérialisable (`json.dumps` lève au milieu) → fichier
  ORIGINAL (préexistant, contenu connu) intact après l'échec, `False` renvoyé,
  **zéro** `.tmp` orphelin (vérifié par `glob`).
- `feedback.enregistrer_event` : event de test enregistré, présence confirmée dans
  `EVENTS` (grep de l'ID), rejeu du même event → `deja_vu: True` (idempotence
  préservée). Event et backup restaurés après (le fichier réel `feedback_events.jsonl`
  ne contient plus le test, vérifié par grep count = 0).
- Run réel de `collecte_signaux.py` avec écriture atomique active : les 3 fichiers
  (`vu.json`, `vu_sas.json`, `signaux_frais.json`) valides JSON après coup (`json.load`
  réussi sur chacun, testés séparément suite à un premier test groupé qui avait
  timeout côté shell — pas côté code), zéro `.tmp` orphelin (`ls data/*.tmp* | wc -l`
  = 0). État restauré ensuite (`vu.json` re-vérifié à 254 entrées, identique à avant).

**Limite connue, non traitée :** `write_json_atomic` protège contre la troncature
mid-write, pas contre une corruption du contenu lui-même en amont (si l'appelant
construit un objet Python incohérent, il sera écrit atomiquement mais restera
incohérent). Ce n'était pas le problème signalé par Fable, donc hors scope assumé.
